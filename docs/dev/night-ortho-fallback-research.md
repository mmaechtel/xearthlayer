# Nachtbeleuchtung über Ortho in X-Plane 12 — Ursache, Optionen für den XEL-Stream, Empfehlung

## 1. Kurzfassung

Die entfernte „eingebackene" Stadtbeleuchtung in X-Plane 12 ist kein Overlay- und kein Autogen-Effekt, sondern eine emissive `TEXTURE_LIT`-Textur der urbanen **Landclass-Terrains im Base-Mesh**: Die Global-Scenery-DSFs referenzieren `lib/g10/terrain10/urban_*.ter`, `library.txt` leitet diese Pfade auf `terrain12/urban_*.ter` / `terrain12/ind_*.ter` um, und genau diese 49 Dateien tragen `TEXTURE_LIT ../textures12/urban_FAR/*_FAR_LIT.dds` + `LIT_FADE_PARAMS … 7000 15000` + `LUMINANCE 600` (Bay's Lighting Mod ersetzt exakt diese neun `_FAR_LIT.dds`). Ein Ortho4XP-Tile (und jedes XEL-Paket) ist ein **vollständiges Base-Mesh-DSF**, das das Global-Scenery-DSF der 1°×1°-Zelle komplett verdrängt; alle seine `.ter` enthalten nur `BASE_TEX_NOWRAP` + `LOAD_CENTER` (+ `NO_ALPHA`/`WET`/`BORDER_TEX`/`DECAL_LIB`), niemals `TEXTURE_LIT` — Ortho4XP hat in 407 Commits keinerlei LIT-Code. Damit ist die Fern-Schicht weg, während die nahen 3D-Lichter (Autogen-Fenster, Straßenlaternen-Objekte aus dem Overlay-Paket) bleiben → harte Abbruchkante. **Konsequenz für den Stream:** Was XEL als DDS liefert, ist irrelevant — ENOENT, schwarze oder transparente Texturen bringen die LIT-Schicht nicht zurück, weil Mesh + Terrain-Typ bereits im Ortho-DSF festgelegt sind. „Fallback auf Standard-Terrain" ist nur erreichbar, wenn X-Plane **statt des Ortho-DSF das Global-Scenery-DSF lädt** — d. h. eine DSF-Substitution im FUSE-Mount, wirksam erst beim (Neu-)Laden des DSF. Empfehlung: Option 3 (sonnenhöhen-gesteuerter DSF-Redirect auf Global Scenery in `Fuse3OrthoUnionFS`, Vorbild ProgrammingDinosaur/autoortho4xplane „Time-Based Exclusion"), optional mit `sim/operation/reload_scenery` über Web API v2; parallel ein 1-Tages-PoC für Option 4 (`TEXTURE_LIT` in Ortho-`.ter` + synthetische `_LIT.dds`), das langfristig das bessere Produkt wäre, aber engine-seitig ungetestet ist.

## 2. Wie X-Plane 12 Nachtbeleuchtung rendert

### 2.1 Zwei Schichten, eine DSF-Datei

| Schicht | Quelle | Reichweite | Datei-Belege |
|---|---|---|---|
| **Nah: 3D-Lichter** | Autogen-Polygone (`POLYGON_DEF lib/g10/autogen/*.ags/.agb/.fac`) → `.obj` mit `TEXTURE_LIT` (Fenster) und `LIGHT_*`; Straßennetz (`NETWORK_DEF lib/g10/roads_EU.net`) platziert Laternen-Objekte (`OBJECT_ALT lib/g10/streetlights/ResLt3.obj` u. a.); Lichtdefinitionen aus `Resources/bitmaps/world/lites/lights.txt` (`BILLBOARD_HW`, `SPILL_HW_DIR`, Sprite-Atlas `1000_lights_close.png`) | Autogen-Bauradius / Objekt-LOD; laut Supnik nicht billig erweiterbar („to double the distance we end up with 4x the AREA of autogen") | `/home/maechtel/X-Plane-12/Resources/default scenery/1000 autogen` (2711 `.obj`, 1602 mit `TEXTURE_LIT`, 105 mit `LIGHT_*`; 0 `.ags/.agb` mit `TEXTURE_LIT`); `1000 roads/roads.net` (1105 `OBJECT_FREQ`, 913 `OBJECT_ALT`, …); `lights.txt` Header („internal file that contains data for the built-in X-Plane lights") |
| **Fern: eingebackene Lichttextur** | `TEXTURE_LIT` in urbanen Landclass-`.ter` des Base-Mesh, erreicht über `library.txt`-Remap | Blendet per `LIT_FADE_PARAMS` (7000–15000 m, Interpretation s. u.) ein; deckt genau die Zone jenseits des Autogen ab | s. 2.2 |

**Wichtig (Verifier-Präzisierung):** XP12 hat *kein* getrenntes Overlay-DSF im Global Scenery. Das Base-Mesh-DSF `+48+011.dsf` enthält gleichzeitig 150 `TERRAIN_DEF`, 178 `POLYGON_DEF` (111 `.ags`, 38 `.agb`, 15 `.for`, 11 `.fac`, 2 `.lin`, 1 `.bch`), 1 `NETWORK_DEF`, 11 `RASTER_DEF`, 0 `OBJECT_DEF`; 13 050 `BEGIN_PATCH`, 45 767 Polygone, 146 723 Straßensegmente (DSFTool-Dump: `scratchpad/xp12_48_011.txt`). Die Unterscheidung lautet also „Terrain-Dreiecke vs. Polygone/Netze *in derselben Datei*", nicht „Base-DSF vs. Overlay-DSF".

### 2.2 Wo die Fern-Schicht konkret liegt (klärt die offene Vorfrage)

- `terrain10/*.ter` enthält tatsächlich **kein** LIT (0 von 6269/12 538 Dateien) — der Ordner ist eine Attrappe.
- Global-Scenery-DSFs referenzieren virtuelle Pfade: `TERRAIN_DEF lib/g10/terrain10/urban_tmp_wet6.ter`, `…/urban_cld_dry1.ter`, `…/urban_tmp_wet_ind1.ter` (Munich `+48+011`: 32 von 150 Defs LIT-fähig; ~30 % aller Patches urban; LA `+34-119`: 44 urbane Defs).
- `Resources/default scenery/1000 world terrain/library.txt` remappt (570 Zeilen): `EXPORT_SEASON spr,sum lib/g10/terrain10/urban_tmp_wet4.ter terrain12/urban_tmp_wet4.ter` / `EXPORT_SEASON fal,win … terrain12/fal/urban_tmp_wet4.ter` (Z. ~13994–14082); die alten terrain10-Exporte sind als `# EXPORT_EXCLUDE` auskommentiert (Z. ~7325–7459).
- `terrain12/urban_tmp_wet4.ter` (vollständig gelesen): `BASE_TEX ../textures12/urban/…`, `COMPOSITE_TEX`, `TEXTURE_NORMAL`, `BORDER_TEX`, **`TEXTURE_LIT ../textures12/urban_FAR/uw6_FAR_LIT.dds`**, **`LIT_FADE_PARAMS 4096 7000 15000`**, **`LUMINANCE 600`**, `#scale = 4096 m`, `FAR 5000 20000 0.0625 ../textures12/urban_FAR/LA2wet_FAR.dds`, `PROJECTED 256 256 …`. Zensus terrain12: 114 `.ter`, 49 mit `TEXTURE_LIT`/`LUMINANCE`/`LIT_FADE_PARAMS` (38 in `terrain12/`, 11 in `terrain12/fal/`), 63 `FAR`. LIT-Texturen: `textures12/urban_FAR/{LA1wet,LA2wet,uw2,uw5,uw6,uw7,uw9,uw11,uw12}_FAR_LIT.dds` (1024², DXT1, 11 Mips).
- Laminar-Primärquelle: 11.20b1-Blog — „X-Plane's night lights come from the autogen, but … X-Plane doesn't build autogen far from the aircraft. Petr has added night lighting textures for the far view to fill in the night sky"; neue `.ter`-Befehle `TEXTURE_LIT`, `LIT_FADE_PARAMS` (https://developer.x-plane.com/2018/03/now-serving-11-20b1/).
- Bay's Lighting Mod v2 (lokal `/home/maechtel/X-Plane-12/X-Plane Mods/Bay's Lighting Mod v2/`) ersetzt genau: die 9 `urban_FAR/*_FAR_LIT.dds`, `lights.txt`, `1000_lights_close.png` + Lua für `sim/private/controls/*`; keine `.ter`. README: „If you are using ortho for your scenery, these 2d distant textures will NOT be drawn. Period." Auf dieser Maschine sind die 9 `_FAR_LIT.dds` am 2026-06-23 überschrieben worden (699 KB, mode 666) — der Nutzer vergleicht also gegen die gemoddete Fern-Schicht.

### 2.3 Rendering-Regeln (Verhalten zur Tageszeit)

- Kein diskreter Nachtschalter für LIT: `sim/graphics/misc/light_attenuation` (DataRefs.txt) — „Since v12 runs photometrically, no light source is *ever* dimmed – the camera itself changes exposure". LIT emittiert immer mit `LUMINANCE` (nits) und wird sichtbar, sobald die Auto-Exposure fällt (https://developer.x-plane.com/2021/11/photometric-lighting-what-is-it-and-why-do-we-need-it/). Ein in ein `.ter` injiziertes `TEXTURE_LIT` bräuchte daher keine Tag/Nacht-Logik in XEL.
- `LIT_FADE_PARAMS <a> <b> <c>`, `LUMINANCE`, `FAR` sind **undokumentiert** (die öffentliche `.ter`-Spec kennt nur `LIT_TEX`/`LIT_TEX_NOWRAP`; https://developer.x-plane.com/article/terrain-type-ter-file-format-specification/). **UNCERTAIN, plausibel:** `<a>` = Texturmaßstab in m (identisch mit `#scale`-Kommentar), 7000/15000 = Fade-in-Beginn/-Ende in m; gestützt durch Binary-Strings `Far Texture Fade-In`, `terrain/far_lit_ratio` in `X-Plane-x86_64`.
- Spec-Aussagen, die für Option 4 relevant sind: `LIT_TEX_NOWRAP` „same as LIT_TEX, except that texture wrapping is turned off"; Standard-Shading-Artikel listet `TEXTURE_LIT_NOWRAP` für `.ter`/`.pol` („edge clamping to avoid bleeding from one side of an orthophoto to another"); `LOAD_CENTER` „affects loading of the base, night, and composite textures" (https://developer.x-plane.com/article/standard-shading-options-for-x-plane-10-scenery/).
- Andere Bedingungsmechanismen sind Ladezeit-only: `EXPORT_SEASON`, `REGION_DREF` („Changes to the datarefs require a scenery re-load"; https://developer.x-plane.com/2015/03/rfc-dataref-driven-library-regions/).

## 3. Warum Orthos das kaputt machen

**Mechanismus (bewiesen):**

1. Ein Ortho4XP-Tile ist ein **Base-Mesh-DSF**: `PROPERTY sim/west/east/south/north` + `sim/creation_agent Ortho4XP`, **kein** `sim/overlay 1`; `bTERT` = `terrain_Water` + eigene `terrain/*.ter`, `bOBJT/bPOLY/bNETW` leer; Raster (elevation, sea_level, soundscape, spr1…win2) werden aus dem Global-Scenery-DSF verbatim kopiert (`/mnt/xplane_data/docker/Ortho4XP/src/O4_DSF_Utils.py:362-467, 632-640, 1069-1091`; DSFTool-Dump `zOrtho4XP_+00+032`: „753 ter, 0 obj, 0 pol"). Höchstpriorisiertes Base-Mesh gewinnt pro Zelle; das Global-Scenery-DSF wird nicht geladen (Laminar KB: „Base meshes exclude everything below them – there can therefore be only one base mesh", https://www.x-plane.com/kb/changing-custom-scenery-load-order-in-x-plane-10/). Lokal belegt: `Log.txt` — 141 geladene DSFs um EDDM, jede Zelle genau ein Base-Mesh mit tris>0 aus `Custom Scenery/zzXEL_ortho/`, `X-Plane 12 Global Scenery` 0-mal geladen obwohl im Index (#820).
2. Jedes Ortho-`.ter` stammt aus einer Vorlage (`O4_DSF_Utils.py:263-357`): `LOAD_CENTER … 4096`, `BASE_TEX_NOWRAP ../textures/<row>_<col>_<PROV><ZL>.dds`, `[DECAL_LIB]`, `NO_ALPHA` | `WET`/`NO_SHADOW`/`BORDER_TEX`/`LOAD_CENTER_BORDER`. Null `TEXTURE_LIT`/`LIT_TEX`/`FAR`/`LIT_FADE_PARAMS`; `git log -S'LIT_TEX'`/`-S'TEXTURE_LIT'` über 407 Commits leer. Gleiches bei Orbx TE GB/US (34 640 `.ter`, 0 LIT), Airwil, St_Barth, BCSceneries; XEL parst nur `BASE_TEX_NOWRAP` (`prefetch/scenery_index.rs:547`).
3. Die urbane Landclass-Klassifikation (welches Dreieck urban ist → welches LIT bekommt) existiert **nur** in den Laminar-Patches; das Ortho-Mesh „only knows about land and water" (Daikan). Sie ist aus dem Ortho-Paket nicht rekonstruierbar.
4. Das Overlay-Paket (`yOrtho4XP_Overlays`, `O4_Overlay_Utils.py:121-176`) kopiert nur `PROPERTY`/`POLYGON_DEF`/`NETWORK_DEF`/Polygone/Segmente mit `PROPERTY sim/overlay 1` → Autogen/Straßen/3D-Lichter bleiben. Nachts: Fensterlichter/Laternen bis zum Autogen-Cutoff, dahinter schwarzer Ortho-Boden.

**Der XOL-/Bay's-Guide** hat den Zwei-Schichten-Befund und die Diagnose („ortho sceneries replace those ground textures and usually have no LIT_TEX night overlay") richtig. Unvollständig/ungenau: (a) es ist nicht „üblicherweise kein LIT", sondern *nie* — es geht nicht um eine fehlende Textur, sondern darum, dass das Ortho-DSF die urbane Terrain-*Klassifikation* verdrängt; (b) der Begriff `LIT_TEX` ist der Legacy-Name, XP12 nutzt `TEXTURE_LIT` + `LIT_FADE_PARAMS`; (c) der Guide sagt nichts dazu, dass die Fern-Schicht über den `library.txt`-Remap `terrain10 → terrain12` kommt und dass Autogen-Lichter erhalten bleiben. Community-Konsens deckt sich (Supnik: „they replaced our terrain entirely and the night lights with it"; Andras Fabian: Landclass braucht „a few hundred generic textures", Ortho „thousands (or 100.000)"; dpny 2024: „no way … with the current scenery engine").

**Konsequenz für die Fragestellung:** „Nachts keine Orthos liefern, damit X-Plane auf Standardtexturen zurückfällt" **funktioniert auf Texturebene nicht.** Fallback setzt voraus, dass X-Plane das Global-Scenery-DSF statt des Ortho-DSF lädt — DSF-Ebene, wirksam beim DSF-(Re-)Load.

## 4. Optionen für den XEL-Stream

| # | Option | Stellt Fern-LIT wieder her? | Wirkzeitpunkt | Aufwand | Verdikt |
|---|---|---|---|---|---|
| 1 | Runtime-Texturschalter (ENOENT / schwarze / transparente DDS nachts) | **Nein** | nur neu geladene DDS/Mips | ~1 Tag | verwerfen |
| 2 | `scenery_packs.ini`-Toggle (`SCENERY_PACK_DISABLED`) | Ja | **nur nach XP-Neustart** | klein | verwerfen (kein Runtime) |
| 3 | **DSF-Redirect auf Global Scenery im FUSE-Mount** (AO4XP-Muster), sonnenhöhen-gesteuert, optional `reload_scenery` via Web API | **Ja** (default terrain12-LIT + Autogen) | neue DSF-Loads sofort; alles nach Reload | 3–5 Tage Kern, +2–3 Tage Reload/Web-API | **empfohlen** |
| 4 | Ortho nachtfähig machen: XEL liefert `.ter` mit `TEXTURE_LIT` + synthetisierte `_LIT.dds` | Ja, sofern XP12 mitspielt (**UNCERTAIN**) | ab nächstem DSF-Load, dann passiv immer | PoC 1 Tag; Produktion Wochen | attraktiv, aber erst nach Experiment 3 |
| 5 | Landclass-Patches im Ortho-DSF belassen (Ortho4XP-Fork) | Ja | Paket-Build | Wochen | verwerfen (Städte auch tags ohne Ortho) |
| 6 | Kosmetik: DDS abdunkeln; Objekt-Lichtpakete; auf Laminar warten | Nein / bedingt | — | — | keine XEL-Aktion |

### Option 1 — Texturschalter
- *Mechanismus:* `lookup()` ENOENT (Präzedenz Wassermasken-Guard `ortho_union_fs.rs:609-636`) oder `read()` liefert schwarze BC1-4096-DDS mit voller Mip-Kette (`validate_dds_or_placeholder` verlangt exakt `EXPECTED_DDS_SIZE` 11 184 952 B; `fuse/placeholder.rs:201-233`, `shared.rs:45-83`).
- *Warum nicht:* Ortho-DSF liefert weiter Mesh + `.ter`. ENOENT auf `BASE_TEX` → Texturfehler/Ersatztextur (UNCERTAIN, was gezeichnet wird), nicht Global-Scenery-Terrain; schwarz → dunkler Boden ohne LIT. Harte Kante bleibt.
- *Wirkzeitpunkt:* nur DDS-Loads nach dem Umschalten (LOAD_CENTER-Paging liest Mips während des Flugs nach → schrittweise, partiell).

### Option 2 — `scenery_packs.ini`
- `sim/operation/reload_scenery` liest die `.ini` **nicht** neu (Supnik: „We do NOT support any of these while flying (or reloading scenery): Changing scenery pack order, Adding scenery packs …", https://developer.x-plane.com/2012/09/scenery-packs-the-new-rules/ Kommentare; SDK: Menüpunkt ≡ `XPLMReloadScenery`). Nur Neustart → als Pre-Flight-Helfer nutzlos, das kann der Nutzer von Hand.

### Option 3 — DSF-Redirect (empfohlen)
- *Mechanismus:* XEL reicht `Earth nav data/**/*.dsf` schon heute passthrough durch (`parallel.rs:91-165` non-lazy Scan; `ortho_union_fs.rs` lookup 564-575, getattr 678-684, readdirplus 955-966, open 994-1007 `fh:0, flags:0`, read 766-799 `fs::read`). Nachts wird die Auflösung für `Earth nav data/<folder>/<tile>.dsf` auf `/home/maechtel/X-Plane-12/Global Scenery/X-Plane 12 Global Scenery/Earth nav data/<folder>/<tile>.dsf` umgebogen (Fallback Demo Areas; kein Treffer → Ortho behalten). **DSF nie verstecken** (AO4XP: „If we hide files, X-Plane finds no terrain data"; X-Plane indiziert Dateipräsenz beim Start/Reload, liest Inhalt pro Tile-Load). Global-Scenery-DSFs referenzieren ausschließlich `lib/…`-Pfade (DSFTool-Dumps +47+011, +34-119, +51+000, +35+139: nur `lib/g10/terrain10`, `lib/g10/autogen`, `lib/g8/*.for`, `lib/g12/beaches.bch`, `lib/g10/roads_EU.net`, 0 `OBJECT_DEF`) → laden ortsunabhängig korrekt inkl. terrain12-LIT.
- *Vorbild:* ProgrammingDinosaur/autoortho4xplane `autoortho/time_exclusion.py` + `autoortho_fuse.py` (Commit 61adad1, Klon in `scratchpad/ao4xp/`): Redirect in getattr/open, Hysterese `sun_pitch < -12°` ein / `> -10°` aus, letzter Zustand bei Telemetrie-Ausfall gehalten, offene DSF-Handles nicht mitten im Lesen umgeschaltet (`_redirected_dsf_fhs`).
- *Wirkzeitpunkt (bewiesen):* nur beim DSF-Open — Tile-Wechsel (~0,6–1° vor der Kante, `docs/dev/xplane-scenery-loading-whitepaper.md`) oder `reload_scenery`; bereits geladene 6–12 Tiles bleiben Ortho (AO4XP-Discussion #434). Log-Belege: DSFs werden je Scenery-Shift frisch über den Mount geöffnet, DEM je Load neu generiert (`Log-2026-08-16-2215.txt` Z. 7537, 8083, 8555, 13024); Unload wird freigegeben (Supnik, https://developer.x-plane.com/2015/06/x-plane-10-40-the-new-dsf-loader/).
- *Kernel-Cache:* passthrough `open()` ohne `FOPEN_KEEP_CACHE` → Kernel invalidiert den Page-Cache je open; Attr-TTL 1 s (`shared.rs:33`). Größe muss in lookup/getattr/readdirplus/read konsistent die des Ziel-DSF sein (`dsf_ErrMissingAtom`-Regression, `ortho_union_fs.rs:1303-1305`). Global-Scenery-DSFs sind 7z-komprimiert → Bytes unverändert durchreichen.
- *Web API (live verifiziert an XP 12.4.3, Port 8086):* `GET /api/v2/datarefs?filter[name]=sim/graphics/scenery/sun_pitch_degrees` → id, WS `dataref_subscribe_values` funktioniert; `GET /api/v2/commands?filter[name]=sim/operation/reload_scenery` → `{"id":15}`; `POST /api/v2/command/{id}/activate {"duration":0}` Route existiert (Test mit id 0 → `invalid_command_id`). Reload selbst wurde **nicht** ausgelöst. XEL nutzt derzeit `/api/v3` (`client.rs:52-58`), read-only, keine Commands.
- *XEL-Änderungen:* (1) `sun_pitch_degrees` (+ optional `percent_lights_on`) in `datarefs.rs`/`SimState` (Assert 12 → 13/14); (2) `NightMode` mit Hysterese, hält Zustand über Telemetrie-Dropouts; (3) Redirect-Seam in `ortho_union_fs.rs` (lookup/getattr/readdirplus/read) mit per-fh-Pfad; (4) Config `[night] enabled, sun_night_threshold, sun_day_threshold, force_reload` (bei späterem Entfernen `DEPRECATED_KEYS`!); (5) optional Web-API-Command-Client für `reload_scenery`, gated durch `paused`/on-ground/Opt-in; (6) Prefetch: Stufe im `filtering.rs` überspringt Regionen im Nachtmodus; (7) TUI-Indikator; (8) `PatchCoverage`-Regionen standardmäßig **ausnehmen** (Nutzer-Patches mit eigenem Mesh); (9) Docs (`docs/dev/fuse-filesystem.md`, `consolidated-mounting-design.md`).
- *Risiken:* Doppel-Autogen (Global-Scenery-DSF trägt dieselben Polygone wie `yOrtho4XP_Overlays`/`yzXEL_overlay`) — **UNCERTAIN**, AO4XP-Nutzer berichten es nicht; `reload_scenery` = kompletter Regionen-Reload (30 s–Minuten, Sim-Freeze), Aircraft-Reset-Berichte vermutlich von AO-Neustarts, nicht vom Reload (UNCERTAIN); XEL-Prefetch/`async_scenery_load_in_progress` müssen einen Reload-Sturm vertragen; Naht Ortho↔Landclass in der Mitte des geladenen Fensters bis Reload/Überquerung; Zellen ohne Global-Scenery-DSF → Ortho behalten.

### Option 4 — `TEXTURE_LIT` in Ortho-`.ter`
- *Mechanismus:* XEL liefert `terrain/*.ter` lazy passthrough → stattdessen Originalzeilen + `TEXTURE_LIT ../textures/<row>_<col>_<PROV><ZL>_LIT.dds` (oder `TEXTURE_LIT_NOWRAP`) + `LIT_FADE_PARAMS 4096 7000 15000` + `LUMINANCE 600`; `_LIT.dds` on demand generiert (dunkles Tile + urbanes Glühen aus Maske: OSM-Straßen/Landuse, VIIRS/Black Marble, oder Laminars `uw*_FAR_LIT.dds`-Muster). Photometrische Pipeline macht es nachts automatisch sichtbar.
- *Voraussetzungen (alle UNCERTAIN/ungetestet):* XP12 wertet `TEXTURE_LIT` auf `BASE_TEX_NOWRAP + LOAD_CENTER` aus (Spec erlaubt es, keine einzige lokale Datei kombiniert es); LIT wird wie Base gepaged (VRAM); `LIT_FADE_PARAMS`-Semantik wie vermutet (sonst „TRON-Straßen" wie bei XPME, Issues #343/#317); `.ter` wird nur beim DSF-Load gelesen → LIT-`.ter` müssen von Beginn an ausgeliefert werden (LIT ist tags passiv → unkritisch).
- *XEL-Änderungen:* `.ter`-Rewriting in FUSE (Pakete + Patches; Kernel-Page-Cache irrelevant, wenn statisch), neuer virtueller DDS-Typ `_LIT.dds` mit eigenem Generator/Provider/Cache-Tier, Attr-Größen, Prefetch, `docs/dev/scenery-packages.md`. Der Datenlieferant (Lichtmaske) ist der harte Teil.
- *UX/Risiken:* Ortho + Fernglühen ohne Kante — bestes Ergebnis, wenn es klappt; synthetisches Glühen wirkt künstlich (XPME-Klagen); doppelte Texturanzahl (Andras Fabian) — mitigierbar mit 512–1024 px LIT, da nur 7–15 km entfernt sichtbar.

### Option 5 — Landclass im Ortho-DSF
- Technisch ausdrückbar (`TERRAIN_DEF lib/g10/terrain10/…` + 5-Plane-Pool), erfordert Neuklassifikation aller Dreiecke aus dem Global-Scenery-DSF, PROJECTED-Terrain auf 7-Plane-Pool UNCERTAIN; Städte sähen auch tags aus wie Default → widerspricht dem Zweck eines Streaming-Tools. Paket-Format-Änderung für alle Nutzer.

### Option 6 — Sonstiges
- DDS nachts abdunkeln (über LOAD_CENTER-Mip-Rereads): rein kosmetisch, ggf. Ergänzung zu Option 4. Objektbasierte Lichtpakete (utd4life Extended Night Lighting, Project World Lights): Overlay, funktioniert mit Ortho, LOD-begrenzt — Nutzerseite. Laminar/neue Engine: keine XEL-Aktion.

## 5. Empfehlung + De-Risking-Experimente

**Primär Option 3** als *Load-Time-Switching* ausliefern (wirkt bei Tile-Wechseln + manuellem Developer › Reload Scenery), automatischen Reload als Opt-in nachreichen, sobald Experiment 2 bestanden ist. Load-Time-Switching ist dabei nicht der Kompromiss, sondern der gewünschte UX-Pfad: X-Plane lädt neue Zellen am *fernen* Rand des geladenen Fensters (~0,6–1° vor der Grenze), d. h. in der Dämmerung kommen zuerst die entfernten Kacheln als Landclass herein — dort, wo Ortho-Detail ohnehin nicht mehr erkennbar ist. Der Ortho↔Landclass-Teppich entsteht am Horizont und wandert nur mit dem Flug nach innen, während die Fernlichter Zelle für Zelle mit der Dunkelheit dazukommen statt schlagartig per Reload. Schwellen so wählen, dass der Flip früh genug in der Dämmerung erfolgt (Experiment 4). **Parallel** 1-Tages-PoC für Option 4.

Alle Experimente sind auf dieser Maschine ohne XEL-Code ausführbar (XP 12.4.3, Web API auf 8086, DSFTool `/mnt/xplane_data/docker/Ortho4XP/Utils/lin/DSFTool`):

1. **DSF-Redirect lädt Global Scenery mit LIT** (~1 h). Region wählen, die zzXEL_ortho bedient und LIT-fähig ist (`+48+011` Munich, `+47+012` LOWS). Temporäres Custom-Scenery-Paket *über* zzXEL_ortho anlegen mit nur `Earth nav data/+40+010/+48+011.dsf` (Kopie aus Global Scenery). XP-Zeit 22:00 lokal, Laden an EDDM, Fernglühen jenseits Autogen-Radius prüfen; `sim/developer/dump_scenery_info_to_log` → Log.txt muss den Global-Scenery-DSF-Pfad und terrain12-`.ter` zeigen. Zusätzlich auf Doppel-Autogen achten (Base-DSF + `yzXEL_overlay`); falls ja, muss der Nachtmodus das Overlay pro Region mit ausblenden (XEL steuert `yzXEL_overlay` nur startzeitlich → als Risiko notieren).
2. **`reload_scenery` via Web API** (~1 h). `GET http://localhost:8086/api/v2/commands?filter[name]=sim/operation/reload_scenery` → id (aktuell 15, ist Session-stabil? per Name auflösen); `POST /api/v2/command/{id}/activate` Body `{"duration":0}` in der Luft, dazwischen DSF im Temp-Paket tauschen. Beobachten: Umschalten Ortho↔Default, Freeze-Dauer, `async_scenery_load_in_progress`, Aircraft-Zustand (Default-Flieger vs. Study-Level), Log.txt-Fehler, XEL-Prefetch/FUSE während des Reload-Sturms.
3. **`TEXTURE_LIT` auf Ortho-`.ter`** (~2 h; Gate für Option 4). In einer lokalen statischen Kopie eines `zOrtho4XP_*`-Tiles (außerhalb des FUSE-Mounts) einige `terrain/<row>_<col>_BI17.ter` einer Stadt editieren: `TEXTURE_LIT ../textures/<row>_<col>_BI17_LIT.dds`, `LIT_FADE_PARAMS 4096 7000 15000`, `LUMINANCE 600`; `_LIT.dds` = herunterskaliertes `textures12/urban_FAR/uw6_FAR_LIT.dds` (BC1 mit Mips). Nachts prüfen: (a) wird überhaupt gerendert; (b) Fade erst ab ~7 km; (c) VRAM/Texture-Browser (Paging mit LOAD_CENTER); (d) Varianten `TEXTURE_LIT_NOWRAP` und ohne `LIT_FADE_PARAMS`.
4. **Schwellen-Kalibrierung** (~30 min). Per WS `sim/graphics/scenery/sun_pitch_degrees`, `percent_lights_on`, `sim/graphics/misc/outside_light_level_r/g/b` abonnieren, Tageszeit durchfahren, Sonnenhöhe bei `percent_lights_on` 0.5/1.0 und bei sichtbar dominantem terrain12-LIT notieren → Defaults für `sun_night_threshold`/`sun_day_threshold` (AO4XP -12/-10, tzimpel-Vorschlag -8/-5).

## 6. Verifikationsstatus und offene Fragen

| Kernaussage | Verdikt | Präzisierung |
|---|---|---|
| Fern-Stadtglühen = `TEXTURE_LIT` der urbanen Base-Mesh-Terrains (terrain12 via library-Remap), nicht Overlay/Autogen | **bestätigt** | DSF referenziert `lib/g10/terrain10/urban_*`; Autogen/Netze liegen im *selben* DSF |
| Ortho4XP-Tile = vollständiges Base-Mesh, alle `.ter` ohne LIT, DDS-Inhalt irrelevant | **bestätigt** | Overlay-Paket bringt Autogen zurück, nie die Terrain-LIT |
| Global-Scenery-DSF nur geladen, wenn kein höherpriorisiertes Base-Mesh; Substitution wirkt pro Tile beim DSF-Load (AO4XP) | **bestätigt** | Präsenz-Index beim Start/Reload, Inhalt pro Tile-Load → DSF nie verstecken, nur Ziel tauschen |
| `reload_scenery` liest `scenery_packs.ini` nicht neu | **bestätigt** | Pack-*Inhalte* werden neu gelesen (Full-Region-Reload, Sim friert) |
| X-Plane öffnet DSFs bei jedem Tile-Load frisch über den FUSE-Pfad | **bestätigt** | mit Verzögerung: geladene Tiles bleiben bis Unload/Reload; ENOENT-Variante UNCERTAIN |
| Web API v2: `sun_pitch_degrees` abonnierbar, `POST /command/{id}/activate` vorhanden | **bestätigt (live)** | Reload nicht ausgelöst; ids sind Runtime-Pointer (je Session per Name auflösen); XEL nutzt v3 |
| Global-Scenery-DSFs referenzieren nur `lib/`-Pfade → laden aus jedem Pack korrekt inkl. LIT | **bestätigt** | nicht live über den XEL-Mount getestet; 7z-DSFs unverändert durchreichen |
| XEL reicht DSFs non-lazy passthrough → Redirect lokal in `ortho_union_fs.rs` ohne Paketformat-Änderung | **bestätigt** | Größen konsistent halten; `read()` liest ganze Datei pro Aufruf (Altlast) |
| `LIT_FADE_PARAMS`/`LUMINANCE`/`FAR`-Semantik | UNCERTAIN | undokumentiert; Interpretation plausibel |
| XP12 wertet `TEXTURE_LIT` auf `BASE_TEX_NOWRAP + LOAD_CENTER` aus | UNCERTAIN | keine Datei/Prior Art; Experiment 3 |
| Doppel-Autogen nach Redirect bei aktivem Overlay-Pack | UNCERTAIN | Experiment 1 |
| Reload-Dauer/Verhalten über großer XEL-Region, Aircraft-Reset | UNCERTAIN | Experiment 2 |
| Was XP bei fehlender `BASE_TEX` zeichnet | UNCERTAIN | irrelevant nach Verwerfen von Option 1 |
